# Как устроен SHFF Dock

Технические подробности, вынесенные из README, чтобы тот остался про продукт.

```
shff-dock/
├── apps/
│   ├── api/          ядро: fastify + dockerode + docker compose
│   └── web/          панель: vite + react
├── packages/
│   ├── shared/       контракт: доменные типы, пути ручек, события сокета
│   └── ui/           дизайн-система SHFF в виде React-компонентов
├── _ds/              вендоренная дизайн-система (токены, css, бандл)
├── docs/screenshots/ картинки для README
├── install.sh        установка на чистую машину одной командой
├── Dockerfile
└── docker-compose.yml
```

## Драйвер — единственное место, где ядро трогает хост

Интерфейс `DockerDriver` (`apps/api/src/core/driver.ts`), две реализации:

| Драйвер | Когда | Что делает |
|---|---|---|
| `MockDriver` | `DOCK_DRIVER=mock` | Выдуманный хост в памяти, собранный по тем же манифестам: стек из пяти сервисов и в моке будет пятью контейнерами. Докер не нужен. |
| `DockerodeDriver` | `DOCK_DRIVER=docker` | Настоящий демон. Читает состояние через dockerode (инспект, статистика, журналы), а всё, что меняет мир, делает через `docker compose` поверх каталога стека. |

Разделение намеренное: инспект должен быть быстрым и частым, а изменения —
воспроизводимыми файлами на диске, а не последовательностью вызовов API, которую
потом никто не повторит руками.

Умолчание выбирается по факту: есть сокет — работаем с докером, нет — с
выдуманным хостом. Раньше умолчанием был `mock`, и это оказалось ловушкой:
панель в контейнере, до которой переменная почему-либо не доехала, молча рисовала
правдоподобные 64 ГБ и отличить её от настоящей можно было только по логам.

## Поток данных

Один вебсокет `/api/stream` отдаёт снимок при подключении, а дальше только
дельты: строки журнала, обновления сервисов, метрики хоста, прогресс задач,
изменения реестра. Пока сокет живой, панель сервер не опрашивает.

Долгие операции возвращают `Job` сразу, прогресс уезжает событиями — HTTP-запрос
не висит, пока тянутся образы.

## Стек — одна карточка

Контейнеры группируются по метке `com.docker.compose.project`, статус и ресурсы
сворачиваются. Контейнеры, поднятые мимо панели, показываются отдельно и
помечаются как чужие (`DOCK_ADOPT_FOREIGN`).

## Раскладка на хосте

Всё, что панель создаёт, лежит в одном месте и нигде больше:

```
/home/dock/
├── stacks/<id>/          стек целиком
│   ├── stack.yaml        манифест, по которому он поставлен
│   ├── compose.yaml      то, что реально исполняется
│   ├── .env              значения инпутов (0600)
│   ├── <конфиги>         отрендеренные prometheus.yml, datasources и прочее
│   └── data/             тома сервисов
├── media/                общая библиотека: music, films, shows, downloads
├── registry/             кэш скачанных манифестов
├── backups/
├── dock.yml              настройки панели
└── state.json
```

`media/` лежит вне стеков намеренно. Качалка, музыкальный сервер и медиатека —
разные стеки, но библиотека у них одна: скачанное qbittorrent'ом в `music`
сразу видит navidrome. Снос любого из этих стеков библиотеку не задевает,
поэтому такие каталоги объявляются томом с `shared: true` и удаляются только
руками.

Каталог стека самодостаточен: скопировал на другую машину, `docker compose up -d`
— получил тот же сервис. Своей базы у панели нет.

Путь `/home/dock` одинаков внутри контейнера панели и снаружи — иначе
bind-монтирования, которые панель пишет в compose-файлы стеков, не разрешились бы
на хосте. Менять его можно, но только целиком, переменной `DOCK_ROOT`.

## Реестр стеков

Стеки в образе не лежат — они живут отдельным репозиторием
[shff-registry](https://github.com/Heisenberg4441/shff-registry) и приезжают по
HTTP. Так каталог пополняется коммитом в реестр, а не пересборкой образа и
переустановкой панели у всех сразу.

Индекс перечитывается при старте, раз в час (`DOCK_REGISTRY_TTL`) и по кнопке в
каталоге. Скачанное кэшируется в `/home/dock/registry`, поэтому недоступный
гитхаб не ломает уже установленные стеки и не мешает ставить новые из кэша —
пустой каталог бывает только на первом запуске без сети.

`path` в `registry.yaml` приходит из интернета и становится путём в кэше, поэтому
проверяется, что запись не уходит за пределы кэша.

Если вы пишете стеки, каталог на диске подключается через
`DOCK_BUNDLED_REGISTRY` — он идёт в основу, удалённый накладывается сверху:
одноимённые стеки перекрываются, остальные добавляются.

Формат `stack.yaml` описан [в README реестра](https://github.com/Heisenberg4441/shff-registry#как-описывается-сервис).

## Кто и где мы

Имя хоста, часовой пояс и оператор попадают не только в шапку панели: они
уезжают в `.env` каждого стека как `DOCK_HOSTNAME`, `DOCK_TZ` и `DOCK_DOMAIN`,
а оттуда — в `TZ` контейнеров и в ссылки вроде `external_url` у gitlab. Ошибка
здесь стоит дороже, чем кажется: неверный пояс сдвигает время во всех журналах
и расписаниях сразу.

Изнутри контейнера правильных ответов нет — `os.hostname()` вернёт идентификатор
контейнера, а пояс будет UTC. Поэтому читается примонтированный корень хоста,
тот же `/host/rootfs`, по которому считаются метрики:

| Что | Откуда |
|---|---|
| Имя хоста | `/etc/hostname`; `localhost` считается незаданным |
| Часовой пояс | `/etc/timezone`, иначе цель симлинка `/etc/localtime` |
| Оператор | `/etc/passwd`, строка с uid, равным `DOCK_PUID` |

Переменные `DOCK_HOSTNAME`, `DOCK_TZ` и `DOCK_OPERATOR` перекрывают
автоопределение. `install.sh` заполняет оператора из `SUDO_USER` — он знает его
точнее, чем можно вывести из uid.

До этого все три значения были константами из макета (`homelab`,
`Europe/Belgrade`, `mikhail`). В уже сохранённом `dock.yml` они означают не
выбор пользователя, а то, что спросить хост панель тогда не умела, — поэтому
при загрузке они молча заменяются определёнными. Значение, отличающееся от
макетного, считается осознанным и не трогается.

## Метрики хоста

Изнутри контейнера `/proc/meminfo` и `statfs('/')` показывают то, что выделено
докеру: на машине с 64 ГБ панель рисовала 30. Поэтому compose монтирует хостовые
`/proc`, `/sys` и корень в `/host/*`, а ядро читает их оттуда. Ограничения cgroup
самого контейнера панели игнорируются — к железу они отношения не имеют.

Если хост не примонтирован, метрики отдаются с пометкой `truthful: false`, и
панель честно пишет об этом полосой сверху вместо красивой неправды.

## Дизайн-система

`_ds/shff-design-system-…/` — как её отдаёт сборщик DS, не правится.
`packages/ui` — те же компоненты в TSX, разметка и классы один-в-один.
Обновить — заменить папку в `_ds/` и путь в `apps/web/vite.config.ts`.

## Сборка и публикация

`.github/workflows/ci.yml` гоняет тайпчек и сборку на каждый пуш и pull request.

`.github/workflows/docker.yml` собирает мультиархитектурный образ
(`linux/amd64`, `linux/arm64`) и публикует его на Docker Hub как
`heisenberg4441/shff-dock`: пуш в `master` уезжает в `:latest` — тот самый, что
тянет `install.sh`, — и дублируется тегом `master-<sha>` на случай отката. Тег
`v1.2.3` даёт `:1.2.3` и `:1.2`.

Публикация требует двух секретов в Settings → Secrets and variables → Actions:
`DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` (Access Token с правом Read & Write, не
пароль). Без них образ всё равно собирается — не выполняется только выкладка.

arm64 собирается через qemu и заметно дольше amd64; с холодного кэша считайте на
полчаса.

## Переменные окружения

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PORT` | `7788` | Порт панели |
| `DOCK_DRIVER` | по наличию сокета | `mock` или `docker` |
| `DOCK_ROOT` | `/home/dock` | Корень раскладки |
| `DOCK_REGISTRY_URL` | `…/shff-registry/master` | Репозиторий со стеками (raw-адрес); `off` — только локальный |
| `DOCK_REGISTRY_TTL` | `60` | Как часто перечитывать реестр, мин; `0` — только вручную |
| `DOCK_BUNDLED_REGISTRY` | — | Реестр на диске в основу удалённого |
| `DOCK_DOCKER_SOCKET` | `/var/run/docker.sock` | Сокет демона |
| `DOCK_NETWORK` | `dock` | Общая сеть панели и стеков |
| `DOCK_ADOPT_FOREIGN` | `true` | Показывать чужие контейнеры |
| `DOCK_PUID` / `DOCK_PGID` | `1000` | Владелец каталогов данных |
| `DOCK_HOSTNAME` | по хосту | Имя машины; пусто — из `/etc/hostname` |
| `DOCK_TZ` | по хосту | Часовой пояс; пусто — из `/etc/timezone` или `/etc/localtime` |
| `DOCK_OPERATOR` | по хосту | Оператор; пусто — владелец `DOCK_PUID` из `/etc/passwd` |
| `DOCK_PROC_ROOT` | `/host/proc` | Хостовый procfs |
| `DOCK_ROOTFS` | `/host/rootfs` | Хостовый корень для места на диске |
| `DOCK_POLL_INTERVAL` | `4000` | Период пересчёта метрик, мс |

## Команды

```bash
npm run dev          # ядро и панель параллельно
npm run build        # shared → web → api
npm run typecheck    # все воркспейсы
npm start            # собранное ядро, оно же раздаёт панель
```

## Известные ограничения

- Шрифты подтягиваются с Google Fonts — так их подключает дизайн-система. Для
  офлайнового билда положить `.woff2` и переписать `_ds/…/tokens/fonts.css`.
- Экран настроек пишет `dock.yml`, но не применяет его к хосту: прокси, TLS и
  cron бэкапов — конфигурация соседних сервисов, а не самой панели.
- `post.health` в манифесте разбирается, но проверку готовности ядро пока не
  выполняет — статус берётся из состояния контейнеров.
- Аутентификации у панели нет: она рассчитана на loopback за reverse proxy.
- Панель ходит в докер-сокет, то есть имеет права root на хосте. Наружу её
  выставлять нельзя.
